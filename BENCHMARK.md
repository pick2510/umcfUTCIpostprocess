# Benchmark: `run_utci.py` / C++ vs `utci_clement`

## Setup

- Case: `Mesh_3x3_parallel_LAD2_disc`
- Probe set: `bbox-padding 10 m`
- Pedestrian positions: `2783`
- Timesteps: `24` (`3600..86400 s`, step `3600 s`)
- C++ workflow threads: `20`
- Clement workflow workers: `40`
- UTCI method on C++ side: `lut`
- Both runs started from a cleaned case:
  - removed `postProcessing/`
  - removed `UTCI/`
  - removed `UTCI_clement/`

## Commands

### C++ workflow

```bash
/usr/bin/time -p /mnt/nvme/UTCI_OF/utci/bin/python run_utci.py \
  --case /mnt/nvme/Mesh_3x3_parallel_LAD2_disc \
  --bbox-padding 10 \
  --output-dir UTCI \
  --utci-method lut \
  -j 20 \
  --force-recompute
```

### Clement workflow

```bash
/usr/bin/time -p /mnt/nvme/UTCI_OF/utci/bin/python run_clement.py \
  --case /mnt/nvme/Mesh_3x3_parallel_LAD2_disc \
  --output-dir UTCI_clement \
  --t-start 3600 --t-end 86400 --t-step 3600 \
  -j 40
```

## Notes on the Clement rerun

The expensive Clement part completed successfully:

- Stage 2a `Tmrt parallel`: `30225.6 s`
- Stage 2b interpolation: `2.9 s`

The original Stage 2c UTCI step failed because `run_clement.py` expects:

- `postProcessing/surfaces/<t>/T_pedestrian.vtk`
- `postProcessing/surfaces/<t>/U_pedestrian.vtk`
- `postProcessing/surfaces/<t>/w_pedestrian.vtk`
- `postProcessing/surfaces/<t>/qrsw_pedestrian.vtk`

On this case, those dense fields had been generated by the cleaned C++ workflow under:

- `postProcessing/surfacesPedestrianAir/<t>/...`
- `postProcessing/surfacesPedestrianRad/<t>/...`

To avoid rerunning the 8-hour Clement VF/Tmrt solve, those existing dense VTKs were linked into `postProcessing/surfaces/<t>/`, and only the missing UTCI stage was rerun.
